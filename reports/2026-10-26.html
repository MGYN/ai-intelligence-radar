1. Wiz 披露「Gheist」：被盗 GitHub token 批量提交 CI workflow，外带 secrets 后删记录（13,500+ 分支 / 850+ 账号）

ANEW国际E/G/CWiz Research 2026-10-25 13:55 EDT（17:55Z / 10-26 01:55 CST）

发生了什么（事实）

  • Wiz 博客（作者 Rami McCarthy、Hila Ramati）披露一场自 2026-09-15 起持续的活动，命名 Gheist：
    • 攻击者用被盗 GitHub token，在受害仓库新建 ci-sync-XXXXXX 分支，提交 .github/workflows/sync-check.yml，提交信息为 ci: sync config；
    • workflow 把环境变量与 toJSON(secrets) 做 base32 编码以绕过日志脱敏，并用 environment matrix 拉取环境级 secrets；随后经 API 下载日志、删除 workflow run；没有独立 C2。
  • 规模（Wiz 统计）：13,500+ 分支、850+ 账号，其中约 2/3 账号已不可见。
  • GitHub 自 2026-07-28 起对公共仓库此类 run 的审批拦截使公共仓库基本未得手；私有仓库与 GHES 有被利用。
  • 10-19 起新增 sync-host 自托管 runner 作业：搜索 31 种 token 格式（含 Anthropic、Hugging Face、Groq、NVIDIA 等 AI 平台密钥）、读 /proc/*/environ、经 Docker socket 逃逸、取云元数据与 K8s ServiceAccount token（Wiz 称该作业有 bug）。
  • 关联：与诱饵仓库、挖矿、PolinRider（Wiz 归于朝鲜相关）、Megalodon 存在重叠；凭证来源含 infostealer 与 Trivy 事件；Wiz 明确称与 GhostAction 不同。
  • 防守建议（Wiz）：狩猎 ci-sync 分支、gheist UA、带 ci-sync subject 的 OIDC 角色假设、.gdmp_* 文件；轮换 secrets；environment 设审批人、OIDC 只信受保护分支、改用 GitHub App / 短期 token、自托管 runner 用一次性实例。

图 1 · Wiz Threat Update「Gheist」文章题图 · 来源：wiz.io/blog

我的判断

  • 这不是新漏洞，而是长期 token = 写 CI = 读全部 secrets 这条链被规模化。真正的新信号是 10-19 加入的 runner 作业专门列出 AI 平台密钥格式——AI API key 已进入通用窃密字典。
  • 「公共仓库被审批拦住、私有仓库与 GHES 没有」说明平台默认值决定了受害面，审批类控制有效但覆盖不全。
  • Wiz 单一来源、GitHub 尚未发文；数字以 Wiz 为准，暂定 A。

未来影响

  • 预计 GitHub 会把「新分支 workflow 首次运行需审批」扩到私有仓库或企业策略默认；
  • 任何让 Agent 持有 PAT 并能 push 分支的产品（Cloud Agent、AI Coding）都在同一攻击面上。

对智能体互联网

  • Agent 对代码托管的委托应是仓库级、分支级、短时、可撤销的凭证（GitHub App installation token / OIDC），而不是用户 PAT；委托凭证需要「不得修改 CI 定义」这类负向 scope。

对 Work·Agent 引擎

  • Cloud Agent 的 push 权限应默认禁止改 .github/workflows/**，或改动须单独审批；
  • Sandbox 不应挂载 Docker socket、云元数据与 SA token；运行时环境变量里不放长期 AI API key，改用网关签发的短期 key。

建议动作：在你自己的组织里按 Wiz 给出的指标查一遍 ci-sync-* 分支与 workflow 删除记录；把「Agent 不得改 CI 定义」写进 Coding Agent 的默认策略；盘点 runner 与 Sandbox 环境里的 AI 平台密钥。

来源：Wiz Research · Gheist

2. 网页可把 AGENTS.md 静默丢进 ~/Downloads，劫持在该目录启动的 Codex / Claude Code

A−NEW（补记：研究 10-22 发布，BleepingComputer 10-25 窗内报道）国际E/C/BForever Security 2026-10-22 / BleepingComputer 2026-10-25 11:49 EDT

发生了什么（事实）

  • Forever Security（Gal Weizman、Omer Samet）称在真实客户机器上发现：~/Downloads 里有一个伪装成工程笔记的 AGENTS.md，而该目录恰好是编码 Agent 的工作目录，Agent 因此尝试安装恶意 npm 包 function-color。
  • 研究者复现（据 BleepingComputer 转述）：
    • 对 OpenAI Codex：用无害载荷（弹计算器）复现，成功率约 90%；
    • 对 Claude Code：用恶意 CLAUDE.md 把 API 流量改指向攻击者服务器，暴露 OAuth token，并由假服务器回传工具调用执行代码，约 50% 成功。
  • 研究者的核心论点：~/Downloads 是网页无需点击即可写入的目录；「OpenAI 或 Anthropic 没有可修的 bug，Agent 按设计读取所在目录的 AGENTS.md」。
  • OpenAI 与 Anthropic 的建议均为在具体项目根目录启动 Agent（BleepingComputer 转述）。

我的判断

  • 指令文件（AGENTS.md / CLAUDE.md / SKILL.md）在 Agent 眼里等于可执行配置，但它们的来源信任目前完全由「在哪个目录」隐式决定。这是协议层缺口，不是某家产品的 bug。
  • 能改写 API base URL 进而拿到 OAuth token，说明「指令文件可改 Agent 自身配置」权限过大。
  • 「真实客户机器」只有厂商单方描述，投放途径未能确认；按补记 A− 处理。

未来影响

  • 预计各家 CLI 会加「工作目录信任」提示（类似 VS Code workspace trust），以及对指令文件中改 endpoint、装包类指令的确认。

对智能体互联网

  • 给 Agent 下指令的文件同样需要出处与签名：谁写的、来自哪个仓库、是否在信任根内；与 Skill 包签名、MCP server 来源校验是同一问题。

对 Work·Agent 引擎

  • Workspace 层：首次进入目录做信任判定，~、~/Downloads、临时目录默认不加载指令文件；
  • 指令文件不得修改模型 endpoint、凭证路径、权限模式，这些只能由用户级配置决定。

建议动作：在你的 Harness 中实现「指令文件加载白名单 + 禁止从指令文件改 endpoint/凭证」；把 ~/Downloads 投放 PoC 纳入回归测试。

来源：Forever Security 原文 · BleepingComputer

3. Kimi 为 K3.1 Pro 订阅限流与额度空耗道歉，一次性返还 25% 月额度；Kimi Code 2.3.2 改为默认单 Agent

A−UPDATE（watchlist 129）国内B/C/I@Kimi_Moonshot 2026-10-25 20:14Z（10-26 04:14 CST）/ kimi-code 2.3.2 2026-10-25 07:59Z

发生了什么（事实）

  • @Kimi_Moonshot 官方帖：
    • 为 K3.1 Pro 订阅计划的限流与不必要的额度消耗道歉，称「These were our issues」；
    • 所有计划的订阅用户获得一次性用量重置：返还 25% 月额度（已用不足 25% 的直接清零），相当于一周用量，PST 当日结束前在用量条体现；
    • 已调整计划参数，减少不必要的 subagent 调用与输出长度。
  • 同日早些时候，Kimi Code 2.3.2（npm @moonshot-ai/kimi-code，07:59Z）的两条改动：
    • 默认直接处理任务，不再主动派生 subagent；如需委派，须在消息、AGENTS.md、skill 或已开启的多 Agent 模式中显式要求（PR #4386）；
    • Agent swarm 只在用户开启 swarm 模式时启动，Agent 不能自行调用 AgentSwarm；因此 kimi -p 与 Zed 等 ACP 客户端中不再可用 swarm（PR #4384）。

我的判断

  • 这是一线厂商第一次公开把「子 Agent 扇出导致订阅额度被吃光」认作自己的问题，并在产品默认值上回撤。与 Anthropic 10-22 的「何时把子 Agent 折回主循环」指南方向一致：多 Agent 默认开启的成本，已经超过它带来的质量收益。
  • 返还额度是补偿，参数调整与默认单 Agent 才是长期变化。

未来影响

  • 编码 Agent 的子 Agent / swarm 会普遍变成显式开关加预算上限；订阅计划会开始按「子 Agent 调用」单独计量或限额。

对智能体互联网

  • 当 Agent 可以自行扩出子 Agent，委托链上的授权与计费主体要能传递：子 Agent 是否继承父 Agent 的 scope 与额度，需要协议层表达。

对 Work·Agent 引擎

  • Agent Loop 中「是否派生子 Agent」应由策略层决定（显式请求、AGENTS.md 规则、预算），而不是模型自主；ACP / headless 模式下默认禁止 swarm 是值得照搬的安全默认值。

建议动作：在你的 Runtime 里给子 Agent 派生加三道闸：显式触发、每会话预算、headless 默认关闭；记录子 Agent token 占比作为可观测指标。

来源：@Kimi_Moonshot · Kimi Code releases

5. 腾讯 CodeBuddy Code 2.176.0：服务模式会话级 A2A 可信与出站开关、确认卡通道、审查拒绝后续聊被执行的修复

B+NEW（快讯 near-miss 收录）国内C/E/Fnpm @tencent-ai/codebuddy-code 2.176.0，2026-10-25 11:08Z

发生了什么（事实）

  • npm @tencent-ai/codebuddy-code 2.176.0 的 CHANGELOG（快讯 19:15 轮核对）列出：
    • 服务模式新增 elicitation 确认卡通道（与 ACP 同形，含 A2A 认证失败与审批卡）；
    • 会话级 remoteAgentsTrusted / remoteAgentsEnabled：A2A 发现源是否可信、是否允许出站；
    • strictMcpConfig；沙箱不可用时默认失败（sandboxUnavailable）；shellEnvironmentPolicy 可丢弃 PATH 与凭据类环境变量；按查询配置 askTools；

  • 这是增量版本，但几项设计都是多租户 Harness 的硬需求：A2A 出站要按会话开关，沙箱不可用要 fail-closed，审查结论要跨轮次持久。最后一条修复说明「拒绝」状态没有落盘是常见缺陷。

对 Work·Agent 引擎：审查结论应作为会话状态持久化，续聊、压缩、恢复后都不得重新评估为允许。

建议动作：对照检查你的 Runtime 在上下文压缩与会话恢复后，被拒工具调用是否仍保持拒绝。

今天正在形成的趋势

  1. Agent 的输入面成为主攻击面：CI workflow、AGENTS.md、OAuth 回调（10-25 的 Inspector）三类「被当成配置的输入」接连出事。
  2. AI 平台密钥进入通用窃密清单：Gheist 的 31 种 token 格式里 AI 平台占一批，与 LiteLLM 事件连成一条线。
  3. 子 Agent 扇出从默认开启回到显式开启：Kimi 改默认值、Anthropic 发指南，成本与可复现性压过并行收益。
  4. 平台把模型选择收进 Agent 订阅：Google 停售单品 Code Assist、Gemini 代理默认 Auto 路由；国内则是集团内数据授权直接接入 Agent（千问 Go）。

对智能体互联网最值得吸收的东西

  1. 负向 scope：委托凭证要能表达「不得改 CI 定义 / 不得改 endpoint」这类禁止项，而不只是允许项（来自 Gheist 与 AGENTS.md 事件）。
  2. 指令来源可验证：AGENTS.md、Skill、MCP server 需要统一的出处与签名字段，Agent 按信任根加载。
  3. 远程 Agent 的「可信」与「可出站」分开授权（来自 CodeBuddy 2.176.0）。

对 Work / Agent 引擎最值得吸收的东西

  1. 子 Agent 三道闸：显式触发、会话预算、headless 默认关闭（来自 Kimi Code 2.3.2）。
  2. 工作目录信任：~、~/Downloads、临时目录默认不加载指令文件，指令文件不得改模型 endpoint 与凭证。
  3. 拒绝状态持久化：安全审查的拒绝结论在压缩、续聊、恢复后保持有效（来自 CodeBuddy 修复）。
