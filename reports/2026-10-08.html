1. 微软 Windows「混合智能」发布会：agent 执行容器 MXC 正式 GA，策略由系统强制、agent 无法给自己加权限；Copilot 本地动作、本地大模型与 RTX Spark 硬件同场

SNEW国际B/C/F/G发布会 10-07 10:00 PT（10-08 01:00 CST）官方博客 10-07

发生了什么

  • MXC（Microsoft Execution Containers）GA：开发者用 JSON 策略声明文件读 / 写 / 拒绝清单、网络入站 / 出站、桌面 / UI 访问，配 Rust / .NET / Node SDK。官方强调策略在 agent 的控制范围之外，agent 不能自行扩权。后端可选：进程容器（Windows 上是 AppContainer，macOS 用 Seatbelt，Linux 用 Bubblewrap）、会话容器（仅 Windows：独立账号与会话，桌面、剪贴板、输入隔离）、WSLc、microVM（实验）、Windows 365 for Agents（GA）。
  • 三种运行模式：Enforcement（强制）、Learning（照样拦截，同时输出 JSON 活动报告，用来收敛出最小权限策略）、Permissive（只记录不拦）。「即将推出」：Intune 下发策略；Entra 在 Agent 365 里区分 agent 活动与用户活动。NVIDIA OpenShell 已集成 MXC（补 OCSF 审计）。
  • 已接入 MXC：GitHub Copilot、OpenClaw、OpenAI Codex、Replit、LM Studio、Unsloth、NVIDIA OpenShell；即将接入：Claude Code、Box、Egnyte、Heidi Health、Hermes Agent、Manus、Perplexity、Raycast、Simular。Meta「Muse for Windows」原生应用（基于 MXC）coming soon。
  • 开源仓库 microsoft/mxc（MIT，2026-02 建库，★1,441，10-08 08:09 CST 仍在推送）。README 列出更多后端（Windows Sandbox、LXC、Hyperlight、Nanvix MicroVM 等）；搜索引擎缓存的旧版 README 曾写「早期预览、勿将任何 profile 视为安全边界」，当前 main 分支已无这段，GA 后的安全边界承诺以官方博客为准，仍需第三方评估。
  • 端侧 / 混合：Copilot+ PC 上的 Copilot 将获得本地上下文、代用户操作和本地模型（「未来数月」）。本地模型示例：MAI Code 1.1 Flash（总 137B / 激活 6.8B，3-bit，256K 上下文）、即将推出的 2-bit Nemotron 70B+、DeepSeek V4 Flash 284B。GitHub「HydraFusion」本地 / 云路由 10 月晚些时候实验预览；OpenClaw 原生 Windows 网关。
  • 硬件：RTX Spark 笔记本即日预售、10-16 发货；Surface Laptop Ultra $2,599 起；Surface RTX Spark Dev Box $5,999（11 月）；DGX Station for Windows 年内（748GB 内存、20 PF FP4，NVIDIA 口径）。

我的判断

这是今年 agent 运行时最重要的平台级发布之一。此前 agent 沙箱是各家自己做（Claude Code 的 bubblewrap/Seatbelt、Codex 的 sandbox、Cursor 的 worktree），微软把它收成「OS 提供、跨三平台、带学习模式和企业策略下发」的公共层，并一次拉来 Codex、Copilot、OpenClaw、OpenShell，Claude Code 也在待接入名单里。等 Intune/Entra 接上，企业就能「按 agent 下发策略、按 agent 审计」，这会让 agent 的执行边界从应用内配置变成 IT 管理对象。保留折扣：GA 当天的隔离强度还没有第三方评估，各后端的防护强度差别很大（进程容器 ≠ microVM）。

往后看

Intune / Entra / Agent 365 的上线时间与 agent 身份字段；Claude Code、Manus、Perplexity 的接入时间；安全研究者对各后端的逃逸测试；HydraFusion 的路由策略是否开放配置。

对智能体互联网

中等相关。Entra「区分 agent 活动与用户活动」意味着企业目录里 agent 将成为独立主体，跨组织调用时对方可以要求「这是哪个 agent、在什么策略下运行」，可作为远程证明（attestation）的雏形。

对 Work / Agent 引擎

强相关。① 策略与执行分离：策略文件由宿主或管理员下发，agent 进程无写权限。② 学习模式：先跑一遍收集真实访问，再生成最小权限策略，比让用户手写清单靠谱。③ 本地 runner 可以直接把 MXC 当 Windows 后端，Linux / macOS 与现有 bubblewrap / Seatbelt 方案同构。

建议动作

  1. 深入调研：读 MXC 策略 schema 与三模式文档，拿自家 runtime 的沙箱配置做一次逐项对照。
  2. 小规模试验：在 Windows runner 上用 Learning 模式跑一组真实任务，看生成的策略能否直接复用。
  3. 关注后续：Entra 的 agent 身份字段与 Intune 策略格式。

4. Atlassian 发布 AMP（Agentic Multiplayer Protocol）：agent 有主人、档案和实时署名，权限分「继承调用者」与「独立服务账号」两种，非人类身份清单即将上线

ANEW国际E/F/B/CTeam '26 Europe 10-07 14:45 CST（10-07 17:18 快讯轮已记为 near-miss）

发生了什么

  • AMP 分三层：In-the-Flow（agent 出现在 Jira/Confluence 等工作流里）；Identity & Shared Presence（每个 agent 有主人、档案、实时署名与「agent 光标」，本地 IDE / 终端里的 agent 会话可桥接成 Jira 里的「Agent Sessions」）；Context & Governance（基于 Teamwork Graph 的上下文；两种权限模式：例如 HR agent 继承发起人的权限，Helpdesk agent 用自己的服务账号；完整审计谁触发、碰了哪些数据；关键步骤人工确认）。
  • 「即将推出」：agent 账号与非人类身份（NHI）清单，覆盖 Atlassian 自家和第三方的 agent、应用、服务账号，可统一撤销；本地会话进 Jira。
  • 同场：Rovo Work（沙箱里的长任务）；Atlassian MCP 重建到 200+ 工具（官方 X 写 220+），token 消耗最多降 25%。
  • 性质：这是 Atlassian 平台内的框架命名，不是公开规范，没有放出协议文本。

我的判断

AMP 把「agent 是协作中的一个成员」做成了产品语义：署名、主人、权限来源、可撤销。其中「继承调用者 vs 独立服务账号」这对概念非常实用，把委托（代表某人）和自主（以自己的身份）明确分开了，几乎所有企业 agent 平台都会遇到这道选择题。名字叫 Protocol，但目前不开放，对互操作的意义有限。

往后看

NHI 清单是否能导入第三方 agent（如通过 MCP/A2A 接入的）；Agent Sessions 是否开放 API；是否与 PAP / A2A 发生对接。

对智能体互联网

强相关（概念层）。「代表谁 / 以谁的身份」应该成为 agent 间调用的必带字段；NHI 清单 + 统一撤销是企业侧接受外部 agent 的前提。

对 Work / Agent 引擎

强相关。多人协作空间里的 agent 署名与版本历史（图中 Confluence 的「Rovo with 某人」），可以直接借鉴到 Workspace 的修改归属；本地会话桥接到工单系统也值得做。

建议动作

  1. 纳入需求：Workspace 修改记录区分「人 / agent / agent 代表某人」三种主体。
  2. 对标架构：在权限模型里显式区分「继承调用者」与「独立服务账号」两种 agent。

5. 补收 + 新进展｜个人 agent 与企业的「接头协议」：PAP（Meta×Sierra）、PACT（Decagon×Instinct）之后，Sierra 10-08 再发 fleming-1，用模型识别来电方是不是 agent

ANEW（快讯已推）+ UPDATE国际E/FPAP 10-06 / PACT 10-06（窗前，10-07 日报漏收）fleming-1 10-08 04:28 CST

发生了什么

  • PAP（Personal Agent Protocol，10-06，11:24 快讯已推）：Meta 与 Sierra 牵头，伙伴 Genesys、Instinct、Rocket、Shopify、Stripe、Walmart。个人 agent 通过网站发现入口，用 OAuth 建立跨渠道的单一会话，由用户决定读写范围，请求可路由到网站、MCP、OpenAPI 或企业自己的 agent。v0.1 规范「本月」发布，截至发稿仍未公开。
  • PACT（Personal Agent Consent & Trust Protocol，10-06，19:14 快讯已推）：Decagon 与 Instinct 共建，Apache-2.0，有规范和参考实现：用 A2A 1.0 Agent Card 做发现，个人 agent 用 JWKS 签名 JWT 证明身份，OAuth 设备码授权，绑定式委托令牌，每次操作返回签名回执；Decagon 同时加入 PAP 工作组。GitHub 仓库目前 ★92。10-08 00:54 CST Decagon 官方 X 再发与 Instinct 的合作推文，无新技术内容。
  • fleming-1（10-08 新）：Sierra 发布实时识别「电话那头是不是 AI agent」的模型，对通话音频持续打分，默认偏保守，识别后怎么处理由企业决定；可用于任何 Sierra 语音 agent。Sierra 的表述是：最好的情况是 agent 自报身份（走 PAP），不自报的就靠 fleming-1。Sierra Summit London 10-15。

我的判断

两周内出现了「自报身份」（PAP/PACT）和「被动识别」（fleming-1）两条互补路线，这正是智能体互联网身份层要的组合：守规矩的 agent 走协议拿到更好的服务，不守规矩的会被识别、降级或转人工。PACT 已经给出可运行的签名和委托令牌实现，比 PAP 走得快；PAP 有 Meta、Shopify、Stripe、Walmart 的分发优势。两者短期是「规范在 PACT、生态在 PAP」的格局，PACT 加入 PAP 工作组后可能合流。

往后看

PAP v0.1 规范文本（重点看身份证明是否采纳 PACT 的 JWKS / 回执设计）；fleming-1 的误判率与申诉机制；电商、支付伙伴的首个落地。

对智能体互联网

强相关。① 发现（Agent Card / 网站入口）+ 身份（签名 JWT）+ 委托（绑定式令牌）+ 回执（签名）四件套，可直接对照自家协议栈逐项补齐；② 「未声明 agent 的被动识别」应作为协议栈之外的配套能力。

对 Work / Agent 引擎

中等相关。Work Agent 代用户对外办事（打电话、下单、客服）时，应默认自报身份并携带委托证明，否则会越来越多地被识别和拦截。

建议动作

  1. 深入调研：精读 PACT 规范与参考实现，评估与 A2A Agent Card、自家身份模型的兼容性。
  2. 关注后续：PAP v0.1 发布当天做逐条对比。

  3. Workspace 的 agent 署名与会话归档（Atlassian AMP）：修改记录区分人 / agent / agent 代表某人，本地 agent 会话可挂到工单或项目上。
